0001 · 为什么 C++ 接口外面要套一层 C 桥接？

dlsym / dlopen / extern "C" 的工程动机

一、一个思想实验

假设你写了一个语音识别引擎，核心类是 VoiceEngine。 你把它编译成 libvoice.so，让 Qt 前端直接链接。

一切正常——直到某天发生以下任何一件事：

  1. 你用 GCC 9 编译 .so，但 Qt 前端用 GCC 11 编译
  2. 你在 CI 上换了一个 Linux 发行版
  3. 你给 VoiceEngine 加了一个 private 成员变量，重新编译 .so，但没有重新编译 Qt 前端
  4. 你把 -D_GLIBCXX_USE_CXX11_ABI=0 传给了其中一个模块
结果： 链接失败（undefined symbol），或者更糟——链接成功，运行时随机崩溃。

这背后只有一个根本原因：C++ 没有稳定的二进制接口（ABI）。

二、核心知识点：C++ ABI 为什么不稳定

我们管编译器输出的二进制层面的"调用约定"叫 ABI（Application Binary Interface）。它包括三样东西：

组件含义C++ 的问题
符号名 函数/变量在 .so 里的字符串标识 C++ Name Mangling：VoiceEngine::start() 可能变成 _ZN12VoiceEngine5startEv——而这个名字随编译器、版本、平台变化1
对象布局 成员变量在内存中的偏移量、vtable 结构 加一个 private 成员就改变偏移；不同编译器 vtable 布局不同2
调用约定 参数如何传（寄存器 vs 栈）、谁清理栈、异常如何传播 C++ 异常不能安全穿越 .so 边界；STL 容器在不同编译器间二进制不兼容3
关键直觉： C++ 编译器的输出是同一份源代码的不同"方言"翻译——两个编译器对同一行 C++ 代码产生的二进制可以完全不同。而 C 的 ABI 在所有主流平台上都是事实标准——它是操作系统本身定义的。

Name Mangling 一窥

同一个 C++ 函数签名，不同编译器产生的符号名：

// void VoiceEngine::start(const char* model, int flags) GCC (Itanium ABI): _ZN12VoiceEngine5startEPKci MSVC: ?start@VoiceEngine@@QAEXPBDH@Z // 而 C 的 extern "C": start // ↑ 所有编译器一致

三、解决方案：C 桥接层

你同事做的事，就是把 C++ 接口翻译成 C，然后用 dlopen/dlsym 运行时加载。下面分层拆解：

第 1 层：extern "C"——关闭 Name Mangling

// voice_c_api.h  —— 对外暴露的头文件（纯 C）
#ifdef __cplusplus
extern "C" {
#endif

// 不透明指针：前端不知道 VoiceEngine 内部长什么样
typedef struct VoiceEngineHandle VoiceEngineHandle;

VoiceEngineHandle* voice_engine_create(const char* config_path);
void               voice_engine_destroy(VoiceEngineHandle* h);
int                voice_engine_start(VoiceEngineHandle* h,
                                      const char* model, int flags);
const char*        voice_engine_get_result(VoiceEngineHandle* h);

#ifdef __cplusplus
}
#endif
extern "C" 告诉 C++ 编译器：这些函数用 C 的链接方式。符号名就是函数名本身，所有编译器一致。不透明指针 VoiceEngineHandle* 替代了 C++ 对象——前端永远不直接看到 C++ 类型。

第 2 层：dlsym/dlopen——运行时加载

// 在 Qt/C++ 前端中，运行时加载语音模块
#include <dlfcn.h>

// 1. 打开 .so（不要求编译时链接）
void* handle = dlopen("libvoice.so", RTLD_NOW);
if (!handle) {
    fprintf(stderr, "%s\n", dlerror());
    return;
}

// 2. 查找函数指针
typedef VoiceEngineHandle* (*create_fn)(const char*);
typedef void               (*destroy_fn)(VoiceEngineHandle*);
typedef int                (*start_fn)(VoiceEngineHandle*, const char*, int);

create_fn  create  = (create_fn)  dlsym(handle, "voice_engine_create");
destroy_fn destroy = (destroy_fn) dlsym(handle, "voice_engine_destroy");
start_fn   start   = (start_fn)   dlsym(handle, "voice_engine_start");

// 3. 使用——和普通函数调用一模一样
VoiceEngineHandle* engine = create("/etc/voice/config.json");
start(engine, "zh-CN-model.bin", 0);
// ...
destroy(engine);
dlclose(handle);

第 3 层：C++ 侧的实现（胶水代码）

// voice_c_api.cpp —— 桥接层实现
#include "voice_c_api.h"
#include "VoiceEngine.hpp"   // 你原来的 C++ 类

extern "C" {

struct VoiceEngineHandle {
    VoiceEngine* impl;  // 包裹你的 C++ 对象
};

VoiceEngineHandle* voice_engine_create(const char* config_path) {
    auto* h = new VoiceEngineHandle;
    h->impl = new VoiceEngine(std::string(config_path));
    return h;
}

void voice_engine_destroy(VoiceEngineHandle* h) {
    delete h->impl;
    delete h;
}

int voice_engine_start(VoiceEngineHandle* h,
                       const char* model, int flags) {
    return h->impl->start(model, flags) ? 0 : -1;
}

const char* voice_engine_get_result(VoiceEngineHandle* h) {
    return h->impl->getResult().c_str();  // 注意生命周期!
}

}

四、多得到了什么？（附赠的好处）

好处为什么
热替换 替换 libvoice.so 文件，前端无需重新编译、甚至无需重启（自己实现 reload 逻辑）
编译防火墙 前端只 include 纯 C 头文件，不依赖任何 C++ 语音引擎的头文件。语音模块内部重构不会触发前端重编译
可选依赖 如果 libvoice.so 不存在，前端可以优雅降级——"语音功能未安装"——而不是启动就 crash
多后端 只要遵守同一个 C API 契约，可以换讯飞/百度/自研引擎——前端一行代码不改
跨编译器兼容 .so 用 Clang 编译，Qt 前端用 GCC 编译——只要通过 C ABI 通信，完全没问题
