0007 · 重定位深入——链接器如何"填地址"

从 call 指令到 ELF 重定位条目——每一步都算给你看

第 0006 课 讲了链接器的全景图。 这节课我们只聚焦一件事：重定位（relocation）——链接器怎么算出该填什么数字。 我们从一个最简单的 C 程序开始，一路追踪到字节级别。

一、从你写的代码到链接器看到的东西

就两行代码，足够说明全部问题：

// main.c
extern void say_hello(void);   // 声明：say_hello 在别处定义
int main(void) {
    say_hello();               // 调用它 —— 但编译器不知道它在哪里
    return 0;
}

编译成目标文件：gcc -c main.c -o main.o

让我们看看编译器在不知道 say_hello 地址的情况下，生成了什么：

图 1：main.o 中 say_hello() 调用对应的机器码。注意 e8 00 00 00 00——call 指令的操作码（e8）后面跟了 4 个零字节占位符。
关键事实 ①： 编译器不知道 say_hello 的最终地址，所以它在 call 指令里放了一个全零的占位符。
关键事实 ②： 编译器同时在 .rela.text 段中留下了一张"纸条"，告诉链接器："请在偏移 0x0A 处填入 say_hello 的地址"。

二、关键概念：call 指令的偏移量不是"绝对地址"

这是最多人卡住的地方。要把这个东西彻底讲清楚。

x86-64 的 call 指令（操作码 e8）后面跟的 4 字节，不是目标函数的绝对地址，而是相对偏移量。

CPU 执行 call 时：跳转目标 = 下一条指令地址 + call 指令中的偏移量

图 2：call 指令是"相对跳转"——CPU 从下一条指令的地址开始，加上指令中的偏移量，算出一个绝对地址再跳过去。

链接器的任务就是：算出这个偏移量应该是多少，然后填进 call 指令的后 4 个字节里。

四、重定位类型不止一种：三种最常见的重定位

x86-64 有几十种重定位类型。与你日常开发最相关的只有这三种：

类型公式适用于例子
R_X86_64_PC32 S + A - P call / jmp（相对跳转） call say_hello
R_X86_64_64 S + A 绝对地址（64 位） mov rax, OFFSET g_volume
R_X86_64_32 S + A 绝对地址（32 位，PIE 禁用） lea eax, [g_volume]

这些信息在 .rela.text 段中，每条重定位记录包含：

图 5：一条重定位记录的三个核心字段。r_offset 告诉链接器"写哪里"，r_info 告诉它"填哪个符号、用什么公式"，r_addend 提供公式中的常数项。

五、一场完整的"手术"：从占位符到正确地址

把上面的知识串起来，完整模拟一次重定位执行过程：

图 6：完整的重定位"手术"。链接器读取 .rela.text 中的指令，在 main.o 的 .text 偏移 0x09 处写入计算出的 4 字节偏移量 0x1F6（小端序：f6 01 00 00）。
等一下——0x401204？say_hello 不是在 0x401200 吗？
差了 4 字节是因为 mov eax, 0x0 这条指令占了 5 字节（0x04–0x08），call 指令从 0x09 开始。前面命令的实际布局会导致这个微小的偏移。在生产代码中，链接器精确跟踪每条指令——这个例子说明的是原理，不是这个特定程序的真实输出。如果你自己跑 objdump，你会发现数值有微小差异，但逻辑完全一样。

六、为什么附加数（addend）是 -5 而不是别的值

很多人对 addend 的值感到困惑。其实它完全取决于CPU 指令的语义。

图 7：addend 的值由编译器和指令类型决定。链接器不需要理解为什么是这个数——它只需要从 .rela.text 中读取 addend，代入公式计算。
实用结论： 你不需要记住每种指令的 addend 值。但你需要知道：addend 是用来补偿"CPU 指令隐式偏移"的修正项。对 call 指令，CPU 的 PC/ RIP 在计算时会指向下一条指令（+5 字节），所以 offset 需要减去这个 5。这个"减 5"就是通过 addend = -5（在 ELF 的 R_X86_64_PC32 中实际是 -4，涉及更微妙的规范差异）来体现的。

七、自己动手验证

在终端跑以下命令，亲眼看看重定位条目的三个字段：

# 第一步：编译 main.o $ gcc -c main.c -o main.o # 第二步：看反汇编——找占位符 $ objdump -d main.o 0000000000000000 <main>: 0: 55 push %rbp 1: 48 89 e5 mov %rsp,%rbp 4: b8 00 00 00 00 mov $0x0,%eax 9: e8 00 00 00 00 call e ← 全是零! e: b8 00 00 00 00 mov $0x0,%eax 13: 5d pop %rbp 14: c3 ret # 第三步：看重定位表——每个字段清清楚楚 $ readelf -r main.o Relocation section '.rela.text' at offset 0x240 contains 1 entry: Offset Info Type Sym.Value Sym.Name + Addend 00000000000a 000a00000002 R_X86_64_PC32 0000000000000000 say_hello - 4 ↑ 偏移 0x0a ↑ 重定位类型 ↑ 符号名 ↑ addend = -4 # 第四步：链接后——占位符消失了 $ gcc main.o voice.o -o myapp $ objdump -d myapp | grep -A6 '<main>:' 401009: e8 f2 01 00 00 call 401200 <say_hello> ← 真实偏移!

你会亲手证实：

  1. 链接前：call 后面是 00 00 00 00（占位符）
  2. .rela.text：记录了偏移 0x0a、类型 PC32、符号 say_hello、addend -4
  3. 链接后：占位符变成了真实的相对偏移量

自测

问题 1：x86-64 的 call 指令（e8）后面跟的 4 字节是：

A. 目标函数的绝对地址（如 0x401200）
B. 从下一条指令到目标函数的相对偏移量
C. 目标函数在文件中的字节偏移
D. 目标函数的符号表索引

问题 2：重定位公式 S + A - P 中，P 代表什么？

A. 目标符号的最终地址
B. 程序入口点地址
C. 被修改字节在内存中的位置（call 指令所在的地址）
D. 页面大小（Page size）

问题 3：call 指令的附加数（addend A）不等于 0，而是负数，这是因为：

A. call 指令的偏移量是相对于下一条指令（+5 字节后）计算的，需要补偿这个偏移
B. 链接器随机选择了一个负值来增加安全性
C. ELF 规范要求所有 addend 必须为负数
D. addend 的值总是和指令长度完全相等
