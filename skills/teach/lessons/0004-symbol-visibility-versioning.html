0004 · 符号可见性控制与 SO 版本管理

从"能跑"到"可以发布"——生产级 C API 的最后一块拼图

0001 课 理解了为什么需要 C 桥接， 0002 课 避开了内存陷阱， 0003 课 看懂了内部机制。 这节课解决一个问题：你的 libvoice.so 给别人用时，怎么保证不出符号冲突、怎么管理版本升级？

一、默认行为的问题：所有符号全部导出

GCC 编译 .so 的默认行为是所有非 static 符号全部导出。你的 VoiceEngine 内部的 helper 函数、第三方库的内联函数——用户全都看得见、链得到。

图 1：默认编译 vs 可见性控制。默认行为下，内部实现细节全部暴露——用户可能意外链接到内部符号，造成符号冲突或 ABI 锁定。

危害不只是"不优雅"

问题后果
符号冲突 如果用户代码中也有一个 g_debug_logger 全局变量，链接时谁覆盖谁取决于链接顺序——这就是经典的"全局符号介入 (symbol interposition)"问题
加载变慢 导出的符号越多，.dynsym 表越大。RTLD_NOW 时需要重定位的条目更多——这在大型 .so（如 Qt 库）上可造成数百毫秒的启动延迟
.so 体积膨胀 linker 不能剥离被引用的符号的相关代码。一个内部 helper 如果被另一个导出的内部函数引用，这条引用链上的所有代码都无法剥离
ABI 意外锁定 用户发现 AudioBuffer::resample 导出了，而且能用，于是依赖了它。你现在改这个函数就是破坏 ABI——哪怕它本来不是 API 的一部分

二、解决方案：默认隐藏 + 选择性导出

第 1 步：编译选项——全局默认隐藏

# CMakeLists.txt 或 Makefile
# 所有符号默认不导出
target_compile_options(voice PRIVATE -fvisibility=hidden)

# 同时隐藏内联函数和模板实例化产生的符号
target_compile_options(voice PRIVATE -fvisibility-inlines-hidden)
-fvisibility=hidden 相当于给所有符号加了 __attribute__((visibility("hidden")))。而 -fvisibility-inlines-hidden 只对 inline 函数生效——即使忘记注解，inline 函数也不会泄漏。

第 2 步：头文件注解——手动标记公开 API

// voice_export.h —— 跨平台的可移植宏

#if defined(_WIN32) || defined(__CYGWIN__)
  // Windows DLL
  #ifdef VOICE_BUILD
    #define VOICE_API __declspec(dllexport)
  #else
    #define VOICE_API __declspec(dllimport)
  #endif
#else
  // Linux / macOS
  #if __GNUC__ >= 4
    #define VOICE_API __attribute__((visibility("default")))
  #else
    #define VOICE_API
  #endif
#endif
// voice_c_api.h —— 只在公开 API 上用 VOICE_API
#include "voice_export.h"

#ifdef __cplusplus
extern "C" {
#endif

typedef struct VoiceEngineHandle VoiceEngineHandle;

VOICE_API VoiceEngineHandle* voice_engine_create(const char* config_path);
VOICE_API void               voice_engine_destroy(VoiceEngineHandle* h);
VOICE_API int                voice_engine_start(VoiceEngineHandle* h,
                                                const char* model, int flags);
VOICE_API int                voice_engine_stop(VoiceEngineHandle* h);
VOICE_API const char*        voice_engine_version(void);

// 注意：没有 VOICE_API 的函数，必须用 static 修饰或放在 .cpp 中
//       static 函数根本不会进入符号表

#ifdef __cplusplus
}
#endif

第 3 步：验证效果

$ nm -D libvoice.so | wc -l            # 119  —— 默认编译，导出 119 个符号
$ nm -D libvoice.so | grep " T " | wc -l  # 43   —— 其中 43 个函数

# 加上 -fvisibility=hidden + VOICE_API 后：
$ nm -D libvoice.so | grep " T "           # 只看到 5 个：
0000000000003a80 T voice_engine_create
0000000000003b10 T voice_engine_destroy
0000000000003ba0 T voice_engine_start
0000000000003c30 T voice_engine_stop
0000000000003cc0 T voice_engine_version
技巧： nm -D 列出动态符号表（.dynsym）——这是 dlsym 真正查找的表。nm 不加 -D 则列出完整符号表（.symtab），包括静态链接用的符号——生产环境中通常用 strip 去掉 .symtab 以缩小体积。

三、SO 版本管理：libvoice.so.1.2.0 的命名规则

只是控制符号可见性还不够。当你要发布 libvoice 的 2.0 版本、与 1.x 不兼容时，怎么让两个版本共存？这就需要 SO 版本命名规范。

gcc -lvoice 查找的文件。一个指向 soname 的符号链接。只在开发环境中存在。 通常放在 -dev 包中 soname libvoice.so.1 运行时查找的文件。记录在 ELF 的 DT_SONAME 字段中。指向 real name 的符号链接。 主版本号 = ABI 版本：不兼容的 ABI 变更时必须递增 实名 libvoice.so.1.2.0 真实的 .so 文件。1 = 主版本 (ABI), 2 = 次版本 (新增API), 0 = 补丁 (bugfix)
图 2：SO 版本命名的三层符号链接链。编译时链接 libvoice.so，运行时解析到 libvoice.so.1（soname），实际加载 libvoice.so.1.2.0（实名）。

如何设置 soname

# 编译 .so 时指定 soname
gcc -shared -Wl,-soname,libvoice.so.1 \
    -o libvoice.so.1.2.0 \
    voice_c_api.o voice_engine.o ...

# 创建符号链接
ln -sf libvoice.so.1.2.0 libvoice.so.1      # soname 链接
ln -sf libvoice.so.1     libvoice.so         # 链接器名（开发用）

# 最终目录结构：
#   libvoice.so       → libvoice.so.1        (只在开发环境)
#   libvoice.so.1     → libvoice.so.1.2.0    (运行时)
#   libvoice.so.1.2.0                        (真实文件)

# 用户的可执行文件在编译时记录了 DT_NEEDED = libvoice.so.1
# 运行时 ld.so 查找 libvoice.so.1，找到后跟随符号链接加载真实文件
$ readelf -d ./my_app | grep NEEDED
 0x0000000000000001 (NEEDED)  Shared library: [libvoice.so.1]

# 升级到 1.3.0 时：
#   修改 libvoice.so.1 → libvoice.so.1.3.0
#   已编译的 my_app 无需重新链接——因为 soname 没变
# 升级到 2.0.0 时（ABI 不兼容）：
#   soname 变成 libvoice.so.2
#   1.x 和 2.x 两个 .so 可以同时安装，互不影响

四、进阶：符号版本脚本（Symbol Versioning）

SO 版本管理解决了"整个 .so 级别的 ABI 兼容"。但如果你的 1.3.0 版本需要同时兼容 1.0 和 1.2 的 API 呢？这就需要符号级别的版本控制。

图 3：符号版本控制允许同一个 .so 同时提供函数的多个版本。旧调用方绑定到旧版本，新调用方绑定到新版本——同一个 soname 下实现 ABI 向后兼容。
// voice_c_api.cpp —— 实现两个版本的 start
extern "C" {

// 新版本 —— 有 timeout 参数
int voice_engine_start_v2(VoiceEngineHandle* h,
                          const char* model, int flags, int timeout_ms)
    __attribute__((__symver__("voice_engine_start@@LIBVOICE_1.3")));
//                          默认绑定 ↑  新代码链接时自动绑定到这个版本

int voice_engine_start_v2(VoiceEngineHandle* h,
                          const char* model, int flags, int timeout_ms) {
    return h->impl->start(model, flags,
                          std::chrono::milliseconds(timeout_ms));
}

// 旧版本 —— 保持原有签名
int voice_engine_start_v1(VoiceEngineHandle* h,
                          const char* model, int flags)
    __attribute__((__symver__("voice_engine_start@LIBVOICE_1.0")));
//                          单一 @ ↑  旧调用方保留了绑定关系

int voice_engine_start_v1(VoiceEngineHandle* h,
                          const char* model, int flags) {
    return voice_engine_start_v2(h, model, flags, 5000); // 默认 5 秒超时
}

}
// libvoice.ver —— 版本脚本（配合 ld --version-script）
LIBVOICE_1.0 {
    global:
        voice_engine_create;
        voice_engine_destroy;
        voice_engine_start;
        voice_engine_stop;
    local:
        *;    // 其余全部隐藏
};

LIBVOICE_1.2 {
    global:
        voice_engine_set_model;
        voice_engine_get_latency;
} LIBVOICE_1.0;  // 继承 1.0 的所有符号

LIBVOICE_1.3 {
    global:
        voice_engine_start;  // 覆盖 1.0 的 start，新签名
} LIBVOICE_1.2;

// 编译:
// gcc -shared -Wl,--version-script=libvoice.ver \
//     -Wl,-soname,libvoice.so.1 -o libvoice.so.1.3.0 ...
诚实地说： 符号版本控制是 GNU/Linux 特有的强大机制，但复杂度很高。大多数项目不需要它——只要严格遵守"主版本号变更 = ABI 不兼容"的契约，让不同 soname 的 .so 共存就足够了。Qt、glibc 这类被数千个程序链接的基础库才真正需要符号版本控制。

自测

问题 1：编译 libvoice.so 时设置 -fvisibility=hidden 后，以下哪项正确？

A. .so 中所有符号对外部完全不可见——dlsym 将无法找到它们
B. 默认全部隐藏，但被 __attribute__((visibility("default"))) 标记的符号仍会导出
C. 只对 C++ 符号生效，extern "C" 函数不受影响
D. 编译失败——必须至少有一个符号可见

问题 2：soname libvoice.so.1 中的 "1" 应该在什么情况下递增？

A. 每次发布新版本——无论改动大小
B. 新增了 API 函数
C. 做了破坏 ABI 兼容的改动（改变现有函数签名、删除函数、改变结构体布局）
D. 修复了一个 bug

问题 3：为什么 -fvisibility-inlines-hidden 也是一个推荐选项？

A. 它让内联函数运行更快
B. 内联函数和模板实例化会在每个引用它的编译单元中生成符号——不加这个选项，这些符号会泄漏到 .so 的导出表中
C. 它是 C++20 的标准要求
D. 它让异常处理更安全
