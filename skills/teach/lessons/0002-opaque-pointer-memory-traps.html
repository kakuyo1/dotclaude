0002 · C 桥接层的内存管理陷阱

不透明指针模式下最容易踩的四个坑

上一课 我们搞清楚了为什么需要 C 桥接层。 这一课讲怎么写才不会埋雷——四个真实工程中高频出现的陷阱。 每个陷阱都遵循同一模式：先看错误代码（你可能正在这么写），再理解为什么炸，最后看修复方案。

陷阱一：c_str() 悬垂指针

你的 C API 返回一个 const char*。在桥接层里，你从 std::string 拿到 c_str() 然后返回。但 std::string 是个临时对象……

❌ 错误写法
// voice_c_api.cpp
extern "C" {

const char* voice_get_result(
    VoiceEngineHandle* h)
{
    auto result = h->impl->getResult();
    //          ↑ std::string 临时对象
    return result.c_str();
    //     ↑ 悬垂! 函数返回后 result
    //       被销毁，指针指向释放的内存
}

}
✓ 修复方案 A：调用方提供缓冲区
// voice_c_api.h
int voice_get_result(
    VoiceEngineHandle* h,
    char* buf, int buf_size);
//   ↑ 调用方拥有内存，没有悬垂问题

// voice_c_api.cpp
int voice_get_result(
    VoiceEngineHandle* h,
    char* buf, int buf_size)
{
    auto& s = h->impl->getResult();
    int n = std::min((int)s.size(),
                     buf_size - 1);
    memcpy(buf, s.data(), n);
    buf[n] = '\0';
    return n;
}
方案 B（API 返回所有权）： 也可以返回 strdup 的拷贝，然后提供 voice_free_string(char*) 让调用方释放。两种方案都是明确所有权归属——方案 A 让调用方提供缓冲区（零拷贝思想），方案 B 让调用方负责释放。

触类旁通

这个问题的本质不是 c_str()，而是"通过 C 边界返回指针时，谁拥有指针指向的内存"。同样的问题会出现在：

  • 返回 std::vector<uint8_t>::data()
  • 返回 QByteArray::constData()
  • 返回任何临时对象的内部指针

陷阱二：跨 .so 边界的 new/delete 不匹配

这是一个没有任何警告、运行时随机崩溃的 bug。

❌ 陷阱场景UNDEFINED BEHAVIOR
// 语音引擎 (.so) 内部——链接了 libc++ A
void* voice_engine_create_buffer(int size) {
    return ::operator new(size);  // 使用 .so 的 operator new
}

// Qt 前端——链接了 libc++ B（不同版本或不同编译器）
void process() {
    void* buf = voice_engine_create_buffer(1024);
    // ...
    ::operator delete(buf);  // 使用前端的 operator delete
    //                        ↑ 堆实现不匹配 → HEAP CORRUPTION
}

为什么？ 每个动态库可能链接自己的 C++ 运行时。.so 的 operator new 使用 .so 的堆，前端的 operator delete 使用前端的堆——两个堆不是同一个。这叫 allocator mismatch。

✓ 核心原则：谁分配，谁释放CORRECT
// voice_c_api.h —— 为每种资源提供对称的 create/destroy

typedef struct VoiceResult VoiceResult;

VoiceResult* voice_result_create(VoiceEngineHandle* h);
void         voice_result_destroy(VoiceResult* r);
//           ↑ 在 .so 内部 delete —— 和 new 在同一堆上
const char*  voice_result_text(VoiceResult* r);

// 前端：
VoiceResult* r = voice_result_create(engine);
printf("%s\n", voice_result_text(r));
voice_result_destroy(r);  // 让 .so 自己释放
这一条也适用于 C 标准库： 如果 .so 用一个 malloc 实现编译，前端用另一个，malloc/free 跨边界同样是 UB。生产级代码应该让 .so 暴露对称的 create/destroy，或者所有分配走同一个分配器（比如传入函数指针）。

陷阱三：C++ 异常穿越 C 栈帧

extern "C" 函数体内如果抛出 C++ 异常，且调用方是纯 C 代码——行为是未定义的。即使调用方也是 C++，异常穿越 extern "C" 边界仍然可能在特定编译器/平台上导致资源泄漏或崩溃。

❌ 危险
extern "C" {

int voice_engine_process(
    VoiceEngineHandle* h,
    const char* audio, int len)
{
    h->impl->process(audio, len);
    //  ↑ 如果这抛出异常 → UB
    return 0;
}

}
✓ 必须吞掉所有异常
extern "C" {

int voice_engine_process(
    VoiceEngineHandle* h,
    const char* audio, int len)
{
    try {
        h->impl->process(audio, len);
        return 0;
    } catch (const std::exception& e) {
        // 记日志、设错误码——但绝不 rethrow
        h->last_error = e.what();
        return -1;
    } catch (...) {
        h->last_error = "unknown error";
        return -2;
    }
}

}

规则很简单： 每个 extern "C" 函数都必须是 noexcept 的——在函数体内部用 try/catch(...) 兜底。C ABI 不认识 C++ 异常。

陷阱四：线程安全——状态归谁管？

C API 里没有 std::mutex 的概念。但你的 VoiceEngine 内部可能有状态读写。谁来保证不透明指针的多线程安全？

❌ 让调用方"注意线程安全"AMBIGUOUS

这是最常见的不作为——API 文档写一句"本接口不是线程安全的"，把责任推给调用方。结果是调用方要么忘了、要么自己加锁但加错了粒度（比如锁了不该锁的），要么做双重加锁。

✓ 两种明确的策略EXPLICIT

策略 A——内部加锁： 每个 API 函数内部获取互斥锁。简单、调用方零负担。适合低频调用。

int voice_engine_start(VoiceEngineHandle* h, ...) {
    std::lock_guard<std::mutex> lock(h->mutex);
    return h->impl->start(...);
}

策略 B——明确文档+可重入保证： 单线程使用，或调用方负责外部同步。在头文件中明确声明，不要留灰色地带。

// voice_c_api.h
//
// ## Thread Safety
// A VoiceEngineHandle MUST be used from a single
// thread at a time. To share across threads, the
// caller must provide external synchronization.
// Different handles may be used concurrently.

四个陷阱速查表

陷阱症状一招制胜
c_str() 悬垂 随机乱码 / SIGSEGV 调用方提供缓冲区，或 strdup + 配套 free 函数
跨边界 new/delete 堆损坏 / double free / 无警告崩溃 对称的 create/destroy，.so 内部自分配自释放
异常穿越 C 帧 未定义行为，通常直接 crash 每个 extern "C" 函数体 try/catch(...) 兜底

自测

问题 1：下面的 C API 函数有什么问题？

const char* get_model_name(VoiceEngineHandle* h) {
    std::string name = h->impl->modelName();
    return name.c_str();
}
A. modelName() 可能抛异常
B. 返回的指针指向已销毁的局部变量——悬垂指针
C. const char* 和 char* 类型不兼容
D. 没有用 strdup 复制字符串

问题 2：为什么跨 .so 边界的 new/delete 可能崩溃，而 malloc/free 通常在 Linux 上能工作？

A. new/delete 是运算符，malloc/free 是函数
B. malloc/free 来自 libc，整个进程通常共享同一个 libc 实例；而 C++ 的 operator new 可能每个 .so 各自链接一份
C. new 会调构造函数，malloc 不会
D. 这题前提错了——malloc/free 跨 .so 边界也一定崩溃

问题 3：extern "C" 函数中漏写 try/catch 兜底——什么情况下一定会出问题？

A. 调用方是纯 C 代码
B. 调用方也是 C++ 代码
C. 任何情况下都是 UB——只是 crash 概率不同
D. GCC 上安全、Clang 上不安全
