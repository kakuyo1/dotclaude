0006 · 链接器到底做了什么

符号解析 · 重定位 · PLT/GOT —— 从 .o 到可执行文件的全过程

前几课我们聚焦在 运行时：dlopen 怎么加载 .so、dlsym 怎么查符号、 桥接层怎么写。这节课我们往上游走——在 dlopen 之前，链接器（linker）已经做了一大堆工作。 理解链接器，你才能真正理解：

  • 为什么 undefined symbol 错误会在链接时而不是编译时报
  • 为什么 C++ 的 name mangling 会让链接器找不到符号
  • PLT/GOT 到底是怎么"自动修复"函数地址的
  • 静态库（.a）和动态库（.so）的本质区别是什么
主要参考：ELF Specification、 Drepper: How To Write Shared Libraries、 Ian Lance Taylor 的 20-part linker essay（LWN）。

一、完整管线：从源代码到进程

当你写完 main.cpp 敲下回车，到程序真正运行起来，中间经过 4 个阶段。链接是第 3 阶段——它夹在编译和加载之间，是很多人理解链条中最模糊的一环。

图 1：从源代码到进程的 4 个阶段。链接器（③）是理解整个体系的核心枢纽——向前连接编译，向后连接加载。
类比帮助记忆： 链接器就像一个"拼图工"。它拿到了多块拼图（.o 文件），每块拼图上有些凸起（导出的符号定义）和凹槽（引用了但未定义的符号）。它的工作是把所有拼图对在一起——填补凹槽、对齐凸起——最终拼出一幅完整的画（可执行文件或 .so）。

二、拆解一个 .o 文件：里面到底有什么

要理解链接器，先要理解它的输入——目标文件（object file）。我们用一段最简单的 C 代码来演示。

// voice_engine.c
#include <stdio.h>

int g_volume = 80;           // 已初始化的全局变量 → .data

void set_volume(int v) {     // 函数定义 → .text
    g_volume = v;
}

void say_hello(void) {       // 函数定义 → .text
    printf("hello\n");       // printf: 未定义符号 → 需要重定位
}

编译成目标文件后：

$ gcc -c voice_engine.c -o voice_engine.o $ file voice_engine.o voice_engine.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV)
.text（代码） .data（已初始化数据） .rodata（只读数据） .bss（未初始化数据） .symtab（符号表） .rela.text（重定位表） .strtab（字符串表）
图 2：voice_engine.o 的内部结构。重定位表 .rela.text 是连接代码和符号的关键——它记录了"哪些位置需要在链接时填入最终地址"。
两种 ELF 文件类型的区别：
  • ET_REL（目标文件 .o）：段尚未分配最终地址，包含重定位信息——链接器的输入
  • ET_EXEC（可执行文件）：段地址已固定，重定位已完成——加载器的输入
  • ET_DYN（共享库 .so）：位置无关代码，可在任意地址加载，但仍可能需要运行时重定位

自己动手：用 readelf 查看 .o 文件

关键观察：printf 的 Ndx = UND 表示它在当前 .o 中未定义——这就是链接器要去找的东西。

三、静态链接：链接器如何合并多个 .o 文件

假设我们有两个目标文件：main.o 调用了 say_hello() 和引用了 g_volume，而 voice_engine.o 定义了它们。链接器需要做两件事：符号解析和重定位。

第一步：符号解析——匹配定义与引用

图 3：链接器将 main.o 的"未定义引用"与 voice_engine.o 中的"定义"匹配。如果找不到定义 → undefined reference to 'say_hello' 错误。

第二步：重定位——把占位符替换成真实地址

符号解析只确定了"哪个符号在哪个文件"，重定位才是真正的"填地址"。

图 4：重定位——链接器把占位符 0x00000000 替换成 say_hello 的真实运行时地址 0x401200。
这就是 C++ Name Mangling 导致链接失败的根本原因！ 链接器是根据字符串名来匹配符号的。如果 main.o 中引用的是 _Z9say_hellov（C++ mangled name），而 voice_engine.o 中因为用了 extern "C" 导出的是 say_hello——名字对不上，链接器就只能报 undefined reference。链接器不关心类型签名，只关心字符串是否完全相等。

四、静态库（.a）：一组 .o 的打包

静态库 .a 文件本质上是一个 .o 文件的归档（ar archive）——就像 .zip 一样把多个 .o 打包在一起，链接器从中按需提取。

图 5：静态链接——链接器从 .a 中提取被引用符号所在的 .o，把代码和数据复制到最终的可执行文件中。未被引用的 .o 不参与链接。
静态链接的优缺点——和你的项目有什么关系？
  • ✅ 可执行文件自包含，不依赖外部 .so，部署简单
  • ❌ 可执行文件很大（每个使用 lib 的程序都有一份副本）
  • ❌ 库更新后必须重新链接——不能运行时替换
  • ❌ 不能使用 dlopen 做插件架构（代码已经"焊死"在可执行文件中）
你的语音项目用 dlopen 而不是静态链接，正是因为需要热替换引擎实现——升级语音引擎不需要重新编译整个应用。

五、动态链接：PLT/GOT 的完整工作流程

动态库（.so）的代码不复制进可执行文件。可执行文件只记录"我需要 libvoice.so 中的 say_hello"。真正的地址解析发生在运行时。

PLT (Procedure Linkage Table) 和 GOT (Global Offset Table) 是实现这一切的机制。这是整个链接体系中最精妙的设计。

5.1 静态图景：PLT/GOT 的数据结构

图 6：PLT/GOT 的静态结构。PLT 是代码（跳板指令），GOT 是数据（地址表）。调用不直接跳到 say_hello，而是经过 PLT → GOT → 真实函数这个间接路径。

5.2 动态图景：首次调用时发生了什么

这是整个动态链接中最值得理解的 5 步过程——建议对照着图一步步在脑子里模拟：

图 7：RTLD_LAZY 延迟绑定的完整流程。首次调用触发解析（5 步），后续调用只需 1 次间接跳转——这就是"懒惰绑定"的名称由来。
现在你应该理解为什么 Lesson 0003 推荐 RTLD_NOW 了： 延迟绑定意味着每个符号的第一次调用都要走这 5 步。在语音实时处理的场景中，你肯定不希望用户说第一句话时触发一大串 _dl_runtime_resolve 调用。RTLD_NOW 在 dlopen 时就一口气把所有 GOT 条目修好——启动稍微慢一点，但运行时完全没有额外开销。

六、一张图总结：静态链接 vs 动态链接

图 8：静态链接 vs 动态链接。核心区别：静态链接在编译时完成所有符号解析和重定位；动态链接把重定位推迟到运行时，通过 PLT/GOT 间接调用。

七、自己动手：追踪动态库的符号和重定位

这些命令是你排查链接问题的基本工具箱。建议在终端里跟着敲一遍：

$ nm voice_engine.o # 查看 .o 的符号表 0000000000000000 T set_volume 000000000000001a T say_hello 0000000000000000 D g_volume U printf $ nm -D /usr/lib/libc.so.6 # 查看 .so 的动态符号表 00000000000534a0 T printf 00000000000a2b10 W puts ... $ objdump -d -j .text voice_engine.o # 反汇编 .text 段 000000000000001a <say_hello>: 1a: 55 push %rbp ... 32: e8 00 00 00 00 call 00 00 00 00 ← 占位符! $ objdump -R myapp # 查看可执行文件需要的动态重定位 DYNAMIC RELOCATION RECORDS OFFSET TYPE VALUE 000000403fe8 R_X86_64_GLOB_DAT __libc_start_main 000000403ff0 R_X86_64_JUMP_SLOT printf $ ldd myapp # 查看可执行文件依赖哪些 .so linux-vdso.so.1 (0x00007ffd...) libc.so.6 => /usr/lib/libc.so.6 (0x00007f...) /lib64/ld-linux-x86-64.so.2 (0x00007f...)
调试题： 如果你在运行程序时看到 undefined symbol: _Z9say_hellov，用 nm -D your.so | grep say_hello 检查 .so 中的实际符号名。大概率你会发现它叫 say_hello（C 链接），而你的代码在找 _Z9say_hellov（C++ mangled name）——这正好是 Lesson 0001 中 extern "C" 要解决的问题。

自测

问题 1：目标文件（.o）中的重定位表（.rela.text）记录了以下哪项信息？

A. 每个段的大小和文件偏移
B. 哪些代码位置需要在链接时填入符号的最终地址，以及对应哪个符号
C. 目标文件依赖哪些 .so
D. 函数的源代码行号映射

问题 2：关于 PLT/GOT 机制，以下哪个描述是错误的？

A. PLT 是只读代码段，GOT 是可读写数据段
B. GOT 条目的初始值指向 PLT 中的下一条指令
C. 每次调用外部函数时，都会重新运行 _dl_runtime_resolve
D. PLT 的间接跳转使得代码段可以跨进程共享

问题 3：对于静态库 .a 和动态库 .so，哪个说法是正确的？

A. .a 包含预编译的二进制代码，.so 包含源代码
B. 使用 .a 时，库代码被复制进可执行文件；使用 .so 时，可执行文件只记录依赖关系
C. .a 文件可以像 .so 一样用 dlopen 加载
D. .so 的加载完全由内核完成，不需要用户态参与
